# Jobs API Implementation Plan

> **For agentic workers:** Execute inline with the available executing-plans skill, task by task, using the checkboxes below. Implementation was subsequently authorized by the user and completed inline on 2026-09-08.

**Goal:** Persist POST /jobs before HTTP 202, expose GET polling, complete the stub worker flow first, then integrate OpenAI Responses.

**Architecture:** Route → validation → controller → submission service → SQLite repository. A single background loop calls a processing service using a fakeable provider interface; only the adapter imports the SDK. Existing AppError definitions and error middleware remain the HTTP boundary.

**Tech Stack:** Node 22.20+ (22.x), TypeScript strict, pnpm 11.21.0, Express 5, better-sqlite3, official `openai` SDK, Vitest, Docker Compose.

**Spec:** [POST jobs spec](../specs/2026-09-08-post-jobs-design.md). Implementation completed on 2026-09-08; see the execution record below.

## Global constraints

- Responses API only; preserve API_KEY, BASE_URL, MODEL. No Chat Completions fallback.
- Persist before returning 202; no provider calls on submission path.
- MAX_ATTEMPTS=1, single worker/process; no implicit SDK retries.
- Never log secrets/prompts/raw SDK objects; never put .env in image.
- No database migrations needed for this scope; use current jobs columns.
- GET /jobs/:id is in scope. No callback sending, retries, idempotency or multiple replicas.
- Acquire SQLite sidecar ownership before recovery; bind HTTP before mutating interrupted jobs.
- Shutdown closes DB only after HTTP drain and worker.done; worker never awaits its coordinator.
- Keep source instructions only in root AGENTS.md; user-selected src/error layout takes precedence over its older errors.ts wording.
- Run automated checks with fakes; no billable network calls.

## Execution order

1. Validation + durable submission repository/service.
2. POST route + parser normalization.
3. GET polling + query service.
4. Provider contract + seeded assessment stub.
5. Worker ownership + atomic processing/recovery.
6. Worker integration, readiness and shutdown; complete stub submit/process/poll.
7. OpenAI Responses adapter, safe logger and secret handling.
8. Handoff and verification.

Public types to define once and reuse (no duplicate DTOs in controllers):

```ts
export interface SubmitJobInput {
  text: string;
  callbackUrl?: string;
}
export interface Usage {
  inputTokens: number;
  outputTokens: number;
}
export interface SummaryResult {
  summary: string;
  usage: Usage;
}
export type JobStatus = 'queued' | 'running' | 'succeeded' | 'failed' | 'dead';
export interface JobRow {
  id: string;
  text: string;
  callbackUrl: string | null;
  status: JobStatus;
  attempts: number;
  summary: string | null;
  errorCode: string | null;
  errorMessage: string | null;
  inputTokens: number;
  outputTokens: number;
  costMicrousd: number;
  createdAt: number;
  updatedAt: number;
}
export interface JobOutcome {
  status: 'succeeded' | 'failed' | 'dead';
  summary: string | null;
  errorCode: string | null;
  errorMessage: string | null;
  usage: Usage;
  costMicrousd: number;
}
export interface JobSubmissionRepository {
  insert(job: JobRow): void;
}
export interface JobQueryRepository {
  findById(id: string): JobRow | undefined;
}
export interface JobProcessingRepository {
  claimNext(now: number): JobRow | undefined;
  finish(id: string, attempt: number, outcome: JobOutcome, now: number): void;
  recoverInterrupted(now: number): number;
}
export interface SummarizationProvider {
  summarize(text: string): Promise<SummaryResult>;
}
```

`ProviderFailure extends AppError` in ai/provider.ts carries `kind: 'input' | 'transient' | 'configuration' | 'invalid_response' | 'unexpected'`,
`usage?: Usage`, `retryAfterMs?: number`; constructor takes ErrorDefinition plus
metadata and cause. Do not redefine codes outside src/error/definition. Error normalization
occurs in adapter; terminal/retry policy remains processing service responsibility.
